# Unicom University — Security Rule

Read `00-master.md` and the MASTER PRD first.

Security requirements are mandatory, not optional polish.

## Trust Model

Treat as untrusted:

- browser/client state;
- request body;
- route/query params;
- uploaded files;
- filenames;
- MIME declarations;
- progress claims;
- exam answers;
- role claims;
- object IDs;
- external provider payloads until validated.

Never trust UI visibility as authorization.

## Authentication

Use a modern secure authentication design appropriate to the selected stack.

Requirements:

- strong password hashing;
- secure session/token handling;
- expiration;
- logout/revocation;
- account status enforcement;
- login throttling;
- password-reset hardening.

After administrative password reset, old sessions must be revocable/invalidated according to the approved design.

Privileged accounts must be architecture-ready for MFA.

MFA for Super Admin is strongly preferred before production.

## Passwords and Secrets

Never:

- store plaintext passwords;
- log passwords;
- commit `.env` with real values;
- expose API keys;
- send password hashes to clients.

Use a secret manager or environment variables.

`.env.example` contains keys/placeholders only.

## Authorization

Use:

`RBAC + resource/object scope`

Server-side checks are mandatory.

Protect against:

- horizontal privilege escalation;
- vertical privilege escalation;
- IDOR/BOLA;
- role self-escalation;
- branch/brand scope bypass.

Trainer must not be able to create/elevate Super Admin unless an explicitly approved future policy changes this.

Supervisor default behavior is scoped read-only monitoring.

Staff may access only assigned learning resources.

## Session Security

If cookie-based:

- HttpOnly;
- Secure in production;
- appropriate SameSite;
- CSRF protection where required.

If token-based, protect storage/rotation/revocation appropriately.

Do not place long-lived privileged credentials in unsafe browser storage.

## CSRF

Any cookie-authenticated state-changing request must have an appropriate CSRF defense strategy.

Do not disable CSRF protection simply because requests originate from the same frontend.

## XSS

Prefer safe framework rendering.

Never inject unsanitized HTML.

If rich content is allowed, sanitize with an approved strategy.

Use a strong Content Security Policy where practical.

## SQL Injection

Use ORM/query parameterization.

Never concatenate untrusted input into raw SQL.

Raw SQL requires parameterization and review.

## SSRF

External URLs must not be fetched blindly from user input.

Restrict schemes/hosts where the application performs server-side retrieval.

Block access to internal metadata/private networks when relevant.

## File Upload Security

For PDF/video uploads validate:

- authenticated permission;
- size limit;
- extension;
- MIME/content signature where practical;
- safe filename;
- storage key generated by server;
- content metadata.

Store privately by default.

Use malware scanning when infrastructure supports it.

Do not execute or render arbitrary uploaded active content.

## File Access

Do not expose permanent unrestricted public URLs for private training materials.

Use authenticated proxy access or short-lived signed URLs according to architecture.

Authorization must be checked before issuing access.

## Rate Limiting and Abuse

Apply rate limiting/throttling to sensitive endpoints such as:

- login;
- password reset;
- AI generation triggers;
- exam submissions where abuse is possible;
- upload;
- expensive report/search operations.

Tune limits to legitimate enterprise use.

## Security Headers

Evaluate and configure production headers such as:

- CSP;
- HSTS;
- X-Content-Type-Options;
- Referrer-Policy;
- frame-ancestor/frame protection;
- permissions policies as appropriate.

Do not enable unsafe permissive values without justification.

## CORS

Use explicit allowed origins.

Do not use broad permissive CORS with credentials.

## Logging and Privacy

Do not log:

- passwords;
- raw reset tokens;
- auth tokens;
- API keys;
- unnecessary personally sensitive values;
- full private document contents without need.

Audit logs should contain enough metadata to investigate administrative actions without leaking secrets.

## Error Handling

Client responses must not reveal:

- stack traces;
- SQL queries;
- filesystem paths;
- secret values;
- provider credentials;
- internal network topology.

Detailed diagnostics belong in protected logs.

## Dependencies

Before production and relevant phases run:

- dependency vulnerability audit;
- secret scanning;
- lockfile review;
- deprecated/insecure package review.

Critical/High exploitable findings must be resolved before production.

## Authorization Tests

Mandatory negative tests include:

- Staff accessing another Staff's resource;
- Staff calling admin endpoint;
- Supervisor accessing outside scope;
- Trainer attempting privilege escalation;
- disabled account accessing authenticated API;
- guessed object IDs;
- signed/private material URL authorization behavior.

## Exam Security

Do not send correct answers to the client before final submission.

Do not trust client-calculated score.

Randomization and grading are server authoritative.

Protect final attempt creation from duplicate submission.

## Progress Security

Do not accept `progress=100` as proof.

Progress endpoints accept evidence/events and calculate authoritative state server-side.

Detect impossible or invalid seek/heartbeat behavior according to `08-progress-engine.md`.

## Production Gate

Security verification must PASS before a phase with security impact is complete.

Before production resolve all known Critical and High security defects, unless a documented risk acceptance is explicitly approved outside the agent's authority.

The agent cannot self-approve security risk acceptance.
